# ADR: Подписка на расписание через iCalendar

- **Дата:** 18.08.2026
- **Статус:** Принято
- **Затрагивает:** `schedule-api`, `schedule-parser2`, PostgreSQL

## Контекст

Пользователям нужна подписка на расписание в Google Calendar, Apple Calendar и Outlook. Статический `.ics` быстро устаревает.

Парсер удаляет будущие занятия и создаёт их заново. Поэтому `lesson.id` нестабилен, а простое исчезновение занятия из следующего `.ics` не гарантирует, что календарный клиент удалит ранее полученное событие.

## Решение

Добавить динамическую подписку:

```http
GET /api/v1/schedule/groups/{group}/calendar.ics
```

Endpoint читает актуальные и отменённые занятия из PostgreSQL и формирует iCalendar. Даты не передаются в URL: адрес подписки должен оставаться постоянным.

Календарь содержит события за последние 14 дней и все будущие занятия, доступные в БД. Источник обычно публикует расписание примерно на месяц вперёд, поэтому отдельный верхний предел не нужен. Отдельный JSON endpoint `/events` не требуется.

## Стабильный UID

Парсер вычисляет UID при вставке занятия:

```text
sha256(group + date + start_time + title + lesson_type)
```

```text
schedule-rsreu-<hash>@rsreu-schedule.ru
```

UID вычисляется PostgreSQL-функцией при запросе. Значение не хранится в `lesson`, а алгоритм не дублируется в Go и Python.

Преподаватели и аудитории намеренно не входят в UID: это изменяемые свойства занятия, а не его идентичность. Если включить их в UID, смена аудитории или преподавателя создаст новое событие и сбросит пользовательские настройки и напоминания.

Изменение даты, времени, названия или типа создаёт новый UID и отменяет старый. Изменение преподавателей, аудиторий, времени окончания или описания сохраняет UID. После каждого успешного обновления парсер увеличивает общую ревизию календаря, используемую как `SEQUENCE`.

Источник не предоставляет постоянный идентификатор занятия, поэтому перенос считается отменой старого события и созданием нового.

## Модель данных

UID вычисляется общей функцией БД:

```sql
CREATE FUNCTION calendar_event_uid(
    group_number text,
    lesson_date date,
    lesson_start timestamp without time zone,
    lesson_title text,
    lesson_type text
) RETURNS text
LANGUAGE sql
STABLE
RETURN 'schedule-rsreu-' || md5(concat_ws('|',
    upper(group_number),
    to_char(lesson_date, 'YYYY-MM-DD'),
    to_char(lesson_start, 'HH24:MI:SS'),
    lesson_title,
    coalesce(lesson_type, '')
)) || '@rsreu-schedule.ru';
```

`md5` здесь не используется для безопасности: нужен только компактный детерминированный идентификатор события.

Общая ревизия календаря хранится отдельно:

```sql
CREATE TABLE calendar_revision (
    id smallint PRIMARY KEY CHECK (id = 1),
    revision bigint NOT NULL DEFAULT 0,
    updated_at timestamp with time zone NOT NULL DEFAULT now()
);

INSERT INTO calendar_revision (id) VALUES (1);
```

Все активные события получают текущую ревизию как `SEQUENCE`. Это намеренно грубая модель: расписание небольшое и обновляется примерно раз в день, поэтому отдельная ревизия для каждого занятия пока не нужна.

Отменённые события хранятся отдельно:

```sql
CREATE TABLE calendar_deleted_event (
    uid text PRIMARY KEY,
    group_number text NOT NULL,
    start_time timestamp without time zone NOT NULL,
    end_time timestamp without time zone NOT NULL,
    title text NOT NULL,
    lesson_type text,
    teachers text[] NOT NULL DEFAULT '{}',
    auditoriums text[] NOT NULL DEFAULT '{}',
    sequence bigint NOT NULL,
    cancelled_at timestamp with time zone NOT NULL DEFAULT now()
);

CREATE INDEX calendar_deleted_event_group_start_idx
    ON calendar_deleted_event (group_number, start_time);
```

Готовые `summary`, `location` и `description` не хранятся: API одинаково форматирует активные и отменённые события из исходных полей.

SQL-проект находится в `calendar-schema.sql`. Его нельзя применять как первую миграцию: сначала текущая схема базы должна быть зафиксирована baseline-миграцией.

## Обновление парсером

Замена расписания выполняется в одной транзакции:

1. Увеличить `calendar_revision.revision` и получить новое значение.
2. Сохранить удаляемые будущие занятия в `calendar_deleted_event`, вычислив UID через `calendar_event_uid` и записав новую ревизию в `sequence`.
3. Удалить старые будущие занятия.
4. Вставить новое расписание без календарных полей в `lesson`.
5. Удалить из `calendar_deleted_event` UID, которые снова появились в новом расписании. UID активных занятий вычисляется той же PostgreSQL-функцией.
6. Удалить отменённые события, завершившиеся более 30 дней назад.

Таким образом, временно удалённые и заново вставленные без изменений занятия не становятся отменёнными. В таблице остаются только UID, отсутствующие в новом расписании.

Упрощённая очистка ложных отмен:

```sql
DELETE FROM calendar_deleted_event deleted
USING lesson active
JOIN "group" student_group ON student_group.id = active.group_id
WHERE deleted.uid = calendar_event_uid(
    student_group.number,
    active.date,
    active.start_time,
    active.title,
    active.type
);
```

При ошибке вся транзакция откатывается: API продолжает видеть предыдущее полное расписание.

## Активное событие

```ics
BEGIN:VEVENT
UID:schedule-rsreu-<hash>@rsreu-schedule.ru
DTSTAMP:20260819T180000Z
DTSTART:20260901T060000Z
DTEND:20260901T073000Z
SUMMARY:📘 Математический анализ
CATEGORIES:EDUCATION,LECTURE
LOCATION:106 C · РГРТУ
GEO:54.6132708;39.7236472
URL:https://www.google.com/maps?q=54.6132708,39.7236472
DESCRIPTION:📘 Лекция Математический анализ\n👤 Иванов Иван Иванович
SEQUENCE:2
STATUS:CONFIRMED
TRANSP:OPAQUE
BEGIN:VALARM
TRIGGER:-PT30M
ACTION:DISPLAY
DESCRIPTION:Пара через 30 минут: Математический анализ
END:VALARM
END:VEVENT
```

## Отменённое событие

API возвращает отменённое событие с прежним UID:

```ics
BEGIN:VEVENT
UID:schedule-rsreu-<hash>@rsreu-schedule.ru
DTSTAMP:20260819T180000Z
DTSTART:20260901T060000Z
DTEND:20260901T073000Z
SUMMARY:Математический анализ
SEQUENCE:1
STATUS:CANCELLED
END:VEVENT
```

После обновления подписки календарный клиент должен заменить ранее полученное активное событие отменённым. Клиент может удалить его из интерфейса или показывать как отменённое до даты занятия; это зависит от клиента, но старое событие не остаётся активным дублем.

Отмена хранится до 30 дней после времени окончания занятия, чтобы календарные клиенты успели её получить.

## Формат

- время из БД интерпретируется в `Europe/Moscow`, а `DTSTART`, `DTEND` и `DTSTAMP` записываются в UTC с суффиксом `Z`;
- `LOCATION` содержит `auditorium.display_name` и краткое название вуза, например `106 C · РГРТУ`;
- если у занятия несколько аудиторий, уникальные `auditorium.display_name` сортируются и перечисляются через запятую, например `106а C, 110 C · РГРТУ`;
- номер подгруппы не хранится и не выводится: пользователь выбирает календарь группы целиком;
- ссылка на вуз передаётся отдельным свойством `URL`, координаты — через `GEO`;
- `DESCRIPTION` содержит тип и название занятия, затем полные имена преподавателей; группа, факультет, курс и аудитория не дублируются;
- `CATEGORIES` содержит `EDUCATION` и тип занятия;
- активные события содержат `VALARM` с `TRIGGER:-PT30M`; отменённые события alarm не содержат;
- календарь содержит стандартные расширения RFC 7986: `NAME`, `SOURCE`, `REFRESH-INTERVAL;VALUE=DURATION:PT1H` и `COLOR:royalblue`; клиент может игнорировать цвет и интервал обновления;
- строки разделяются `\r\n`;
- специальные символы экранируются по iCalendar;
- строки переносятся после 75 октетов без разрыва UTF-8 символов;
- файл завершается переводом строки.

## HTTP-ответ

```http
Content-Type: text/calendar; charset=utf-8
Content-Disposition: inline; filename="schedule-<group>.ics"
Cache-Control: public, max-age=300
```

Кэш в памяти и Redis не добавляются. `ETag` и `Last-Modified` откладываются до появления надёжной версии последнего обновления расписания.

## Размещение кода

`schedule-api`:

- route и handler — `internal/http/handlers/v1/schedule.go`;
- запрос активных и отменённых событий с вычислением UID — `internal/repo/repo.go`;
- сборка iCalendar — `internal/services/calendar.go`;
- модели — `internal/models`.

`schedule-parser2`:

- вычисление UID и синхронизация отмен — `db.py`.

Новый сервис и внешняя зависимость не добавляются.

## Ошибки

- неизвестная группа — `404 Not Found`;
- ошибка БД или генерации — `500 Internal Server Error`;
- ошибки возвращаются как JSON, а не как `.ics`.

## Проверка

Автоматические проверки:

- одинаковые занятия получают одинаковый UID;
- изменение аудитории или преподавателя не меняет UID;
- успешный запуск парсера увеличивает общую ревизию и `SEQUENCE`;
- ошибка парсера откатывает увеличение ревизии;
- неизменённое занятие не остаётся в `calendar_deleted_event`;
- удалённое занятие сохраняется с прежним UID;
- перенос создаёт новое событие и отменяет старое;
- `.ics` содержит `STATUS:CANCELLED` и `SEQUENCE`;
- кириллица, экранирование и московское время обрабатываются корректно;
- ошибка обновления откатывает всю транзакцию.

После реализации подписка вручную проверяется в Google Calendar, Apple Calendar и Outlook, особенно после удаления и переноса занятия.

## Последствия

Преимущества:

- удалённые занятия перестают быть активными после обновления подписки;
- UID вычисляется только парсером и хранится в БД;
- ложные отмены после полного обновления парсера удаляются в той же транзакции;
- не нужны OAuth и отдельные интеграции с календарными провайдерами.

Ограничения:

- частоту обновления выбирает календарный клиент;
- клиент может показывать событие как отменённое вместо полного скрытия;
- перенос занятия выглядит как отмена и создание нового события.

Если полная замена расписания станет источником других проблем, следующим шагом будет переход парсера на `UPSERT` с постоянным `revision` и статусом занятия прямо в `lesson`.
