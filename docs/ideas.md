# Идеи

## Плоский список занятий

Если JSON-список конкретных занятий понадобится frontend или другому клиенту, добавить endpoint:

```http
GET /api/v1/schedule/groups/{group}/events?from=2026-09-01&to=2026-12-31
```

Параметры `from` и `to` ограничивают период. Без них API может возвращать текущую и следующую недели.

Для экспорта календаря этот endpoint не нужен: `/calendar.ics` должен получать занятия напрямую из репозитория.

## Roadmap после календарного экспорта

### 1. Миграции и деплой

- Подключить Goose и хранить SQL-миграции в репозитории.
- Добавить команды для применения миграций локально без Docker.
- В CI проверять сборку, тесты и корректность миграций.
- При деплое сначала применять миграции, затем запускать новую версию API.
- Добавить резервное копирование базы и документировать откат релиза.

### 2. Тестовое покрытие

- Покрыть календарный экспорт: формат событий, UTC, обновления и отмены.
- Добавить тесты репозитория для выборки активных и удалённых занятий.
- Покрыть критические сценарии парсера небольшими тестами без Docker.
- Зафиксировать минимальный порог покрытия в CI после появления стабильной базы тестов.

### 3. Рефакторинг парсера

- Разделить загрузку страницы, разбор расписания и запись в базу.
- Убрать повторное удаление занятий и оставить одну транзакционную синхронизацию.
- Сделать обработку изменений и отмен занятий явной и проверяемой.
- Сократить дублирование при разборе преподавателей, аудиторий и подгрупп.

### 4. Рефакторинг бота

- Отделить Telegram-обработчики от клиентов API и форматирования сообщений.
- Убрать дублирование запросов и отображения расписания.
- Добавить тесты команд и пользовательских настроек без обращения к Telegram.
- После стабилизации API перевести бота на единые модели и endpoint-ы расписания.
